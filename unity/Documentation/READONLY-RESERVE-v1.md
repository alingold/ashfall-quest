# Read-only reserve boundary v1

`WeaponHandling.TryReadReserve(out int available,out long revision)` reads the actual revisioned reserve consistently on the trusted owner lane and rejects unsupported, negative or interveningly mutated metadata. It does not expose a mutable reserve, grant ammo or authorize a weapon operation. `SharesReserveWith(WeaponHandling other)` compares actual reference identity without returning that object. The existing `VersionedReserve` getter remains internal to the weapon owner. Cross-assembly readers must use the read-only APIs; checkpoint code can reject actual shared reserves by pairwise comparison of at most64 handlers instead of holding raw mutable objects.

Root replaced the old direct internal-getter accesses in InventoryTransfers.WorldState. Evidence phase15/reserve-boundary-validation.json separately compiles Core, Weapon, Inventory, Pickups and the four-file InventoryTransfers consumer, then passes six actual metadata/alias/read-only assertions. It intentionally uses pinned phase13 module sources plus the exact new accessor/current consumer; it is not evidence for a moving whole-tree graph. The active InventoryRecovery candidate recorded prior internal-access dependency drift and must qualify against this boundary in its next integration review.
